# TraceX hosted deployment

This setup hosts the React frontend on Vercel, the FastAPI service on Render, and application data in MongoDB Atlas. Secrets belong in provider dashboards and must not be committed to Git.

## 1. Create the MongoDB Atlas database

1. Create an Atlas project and a cluster.
2. Create a database user for TraceX and save its password in your password manager.
3. In **Network Access**, allow connections from the Render service. Render's public outbound IPs depend on its plan and region; use Render's documented outbound IP ranges when available. If your Render plan does not provide fixed outbound IPs, Atlas requires an allow rule that covers Render's outbound addresses. Restrict this as much as your plan permits.
4. Choose **Connect → Drivers** and copy the `mongodb+srv://...` connection string. Replace the password placeholder only in Render's dashboard; do not put the real URI in this repository.

## 2. Deploy the API on Render

1. Push this repository to GitHub and open the Render Dashboard.
2. Choose **New → Blueprint**, select `gopika2602/TraceX`, and select the `main` branch. If the existing Render service is still connected to the older `backend` branch, change its connected branch to `main` (or otherwise deploy the current `main` commit) so it includes the admin-bootstrap code.
3. Confirm that Render finds the root `render.yaml` and creates the `tracex-api` web service.
4. When prompted, enter the Atlas connection string as `MONGODB_URI`. Render generates `JWT_SECRET_KEY` from the Blueprint. Keep that value private and do not rotate it casually, because sessions signed with the old key will stop working.
5. Set `ADMIN_EMAIL` and `ADMIN_PASSWORD` in Render before the first deploy when the Atlas `users` collection is empty. Use your own email and a unique, strong password. The service creates this account as an Admin once; it will not create or update any users after the collection contains a user. Never put real values in Git or commit them to `.env` files. After confirming you can sign in, remove these two bootstrap variables from Render.
6. Confirm these API service variables:

   | Variable | Value |
   | --- | --- |
   | `MONGODB_URI` | Atlas driver connection string (secret) |
   | `ADMIN_EMAIL` | First Admin email (set only for initial bootstrap) |
   | `ADMIN_PASSWORD` | First Admin password (secret; set only for initial bootstrap) |
   | `MONGODB_DATABASE` | `tracex` (set by the Blueprint) |
   | `CORS_ORIGINS` | `https://tracex-app.vercel.app,http://localhost:5173,http://127.0.0.1:5173` (set by the Blueprint) |
   | `APP_ENV` | `production` (set by the Blueprint) |
   | `JWT_SECRET_KEY` | Generated by Render; keep private |
   | `SESSION_COOKIE_SECURE` | `true` (set by the Blueprint) |
   | `SESSION_COOKIE_SAMESITE` | `none` (set by the Blueprint for Vercel-to-Render auth cookies) |
   | `PORT` | Render injects this automatically. The container binds to it and listens on `0.0.0.0`; do not hardcode a production port. |

7. Wait for the service to deploy. Open `https://<your-render-service>.onrender.com/health` and confirm it returns HTTP 200. Then open `/health/ready`; it should report `ready` and `database: connected`. A healthy `/health` response alone does not prove Atlas connectivity.
8. Copy the Render service's public base URL, for example `https://tracex-api.onrender.com`, without a trailing slash.

## 3. Configure the Vercel frontend

1. Open the existing `trace-x` project in Vercel and go to **Settings → Environment Variables**.
2. Add `VITE_API_BASE_URL` with the Render API base URL. Select **Production** (and **Preview** too if you want preview deployments to use the same API).
3. Set `VITE_USE_MOCK` to `false` for Production so cases and analysis use backend data.
4. Redeploy the latest `backend` commit. Vite reads these variables at build time, so changing them without a new deployment does not update the frontend bundle.
5. Open `https://tracex-app.vercel.app/login`. Sign in and confirm the browser can reach the API. The backend's allowed origins include this Vercel domain, and its session cookie is configured for secure cross-site requests.

## Configuration reference

Backend variables:

- `MONGODB_URI` — required Atlas connection string; secret.
- `ADMIN_EMAIL` and `ADMIN_PASSWORD` — optional first-admin bootstrap credentials. When both are set and `users` is empty at backend startup, the backend creates one Admin with the normal password hash. It does nothing if the collection already contains any account. Set these only for initial bootstrap and remove them after confirming sign-in.
- `CORS_ORIGINS` — comma-separated exact browser origins; defaults include the Vercel production domain and localhost development origins.
- `PORT` — injected by Render; the Docker start command uses it and falls back to `8000` for local use.
- `JWT_SECRET_KEY` — required in production; generated by the Render Blueprint.
- `APP_ENV=production`, `MONGODB_DATABASE=tracex`, `SESSION_COOKIE_SECURE=true`, and `SESSION_COOKIE_SAMESITE=none` — set by the Blueprint for production.

Vercel variables:

- `VITE_API_BASE_URL` — required API base URL, set for each environment that should use the backend.
- `VITE_USE_MOCK=false` — recommended for Production so case data uses the backend.

The frontend permits a localhost API default only during Vite development. A production build without `VITE_API_BASE_URL` displays a configuration error rather than silently sending requests to a laptop address. Production builds also reject `VITE_USE_MOCK=true` and direct the operator to disable it. `/health` is a process health check; `/health/ready` checks MongoDB connectivity.
